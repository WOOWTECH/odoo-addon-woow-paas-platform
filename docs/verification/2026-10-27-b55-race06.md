## Provider semantics investigated

Cloudflare's current Access Applications API documents:

- creation as `POST /accounts/{account_id}/access/apps`;
- update as `PUT /accounts/{account_id}/access/apps/{app_id}`;
- readback as `GET /accounts/{account_id}/access/apps`;
- exact list filters `name`, `domain`, and `exact=true`, plus pagination;
- no Access-application create idempotency key and no documented
  read-after-write consistency guarantee.

Primary references:

- https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/
- https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/methods/list/
- https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/methods/create/

Consequences used in the implementation:

1. Provider idempotency cannot be claimed or synthesized.
2. An empty exact lookup cannot authorize retry because a prior successful POST
   could be temporarily invisible.
3. Multiple exact matches cannot be selected automatically.
4. One byte-for-byte exact name+domain result can be safely adopted by ID after
   an administrator deliberately invokes review; the next normal sync uses PUT,
   not a second POST.

## Implementation

- Added read-only operator endpoint `POST /api/access/review-application`.
- Operator performs the complete paginated Cloudflare list using exact filters,
  then independently rechecks returned `name` and `domain` byte-for-byte.
- Response is one of `unique`, `absent`, or `ambiguous`; only `unique` carries an
  app ID.
- Added Odoo client wiring and
  `action_review_and_adopt_provider_app(reason)`.
- Review still requires `base.group_system` and a specific audit reason.
- Zero/multiple/error results leave the durable fence in `dispatching`.
- The former free-form `action_record_verified_app(id, reason)` now rejects all
  supplied IDs, preventing typo/wrong-resource adoption.
- Batch54's pre-effect automatic recovery remains unchanged. No post-effect
  automatic POST retry was added.

### Independent post-marker failure injection

Command:

```text
uv run --with-requirements requirements.txt pytest -q -m integration \
  tests/test_race06_post_marker_process.py
```

Result: **1 passed**.

The test starts a real loopback HTTP provider in a separate spawned process.
The provider durably records one exact-owned application and then withholds its
POST response. The caller process is sent `SIGKILL` in that post-effect,
pre-receipt window. A fresh caller invokes the production readback method,
obtains the unique exact ID, and verifies the provider observed exactly one
POST. It then deletes the exact-owned application and verifies an empty
inventory.

This proves the candidate's review/adoption mechanism under native process
failure. It does **not** prove Cloudflare's timing/consistency behavior and is
not substituted for the original live-provider oracle.
