#### C. (b) Deactivate `project.project_public_members_rule` 獨立驗證

**結論：engineering-necessary, 非可避**。

獨立分析的理由（與 implementation 主張一致）：

1. **OR 語意確認** — Odoo 18 對 record rule 的 evaluation：對使用者所屬的每個 group，apply 該 group 上的 rules（多個 rule = AND）；不同 group 的 rule sets = **OR**。Odoo std `project_public_members_rule` 套在 `base.group_user`，新 `project_rule_workspace_member` 也套在 `base.group_user`。**同 group 多 rule = AND**，所以理論上兩 rule AND 後會更嚴。

   但 Odoo std rule 的 domain `['|', ('privacy_visibility', '!=', 'followers'), follower-check]` 內含 **always-true leg**（`privacy_visibility != 'followers'` 對絕大多數 project 為 true，因為預設值是 `'employees'`）。AND-with-always-true ≈ 透過 std rule 的部分被新 rule 涵蓋，**理論上不會放鬆**。

2. **實測風險點** — 但實作層級有另一個現實問題：Odoo std rule 對 partial domain 與 ORM 階段的 evaluation order 可能讓使用者看到 std rule 的「短路」放行。Deactivate 是 root-cause-correct 修補，避免 implicit AND 行為 drift。

3. **替代方案評估**（為何不能避）：
   - **改 std rule 的 domain（不 deactivate）**：可行但跨模組改 Odoo std 行為，跟 deactivate 同等侵入。
   - **新增 NOT clause 在自家 rule 上**：無效——多 group rule 是 OR，自家 rule 加 NOT 不能限制 std rule 行為。
   - **拉新 security group 取代 base.group_user**：scope 暴漲（要改 user 設定 / module install hook），與 plan §現況「workspace member 透過 `base.group_user` 進入」相容性差。
   - **完全靠 controller 端 sudo + 顯式 filter**：plan D8=A 已論證 ORM 路徑（M2M widget）會繞過 controller。

   → **(b) 是唯一 root-cause-correct 解，符合「縮緊到 multi-tenant 隔離」目標**。

4. **影響面**（project 端 acceptable）：
   - **`base.group_user` 沒 `project.group_project_user`**：失去「`privacy_visibility != 'followers'` project 全可見」這條腿；改為「workspace member 或 project member」。對 PaaS 是 tightening。
   - **`project.group_project_user`（project user，含 base.group_user via implied_ids）**：security-auditor 確認 — pre-refactor `project_public_members_rule` 是 group_project_user 在 project.project 上唯一 OR-able permissive rule，deactivation 後 group_project_user 也受 `project_rule_workspace_member` 約束（implementation 已將此 rule 同套 `project.group_project_user`，`ir_rules.xml:71`）。這是**有意的 scope expansion**：pre-refactor Project User 可看所有 non-followers project，post-refactor 只看 workspace member。**符合 plan D3=A 隔離目標**。
   - **sudo context**：完全 bypass record rule，不受影響。`controllers/ai_assistant.py` 等仍走 sudo，行為不變。
   - **Demo data / 非本 module project consumer**：本 Odoo instance 內 grep 確認 `_inherit = 'project.project'` 只有本 module（`src/models/project_project.py:5`），無第三方 consumer。**PR draft 第 151 行的聲明驗證 ✓**。

5. **rollback**：PR draft 提供的 SQL（`UPDATE ir_rule SET active=true WHERE id IN (SELECT res_id FROM ir_model_data WHERE module='project' AND name='project_public_members_rule')`）正確。可逆。

6. **但 task 端對稱的 deactivation 缺漏 → §E HIGH BLOCKER**。Project 端的這個分析顯示 implementation 對「Odoo std rule OR 語意」的處理在 project 端是正確的；task 端缺漏的是「相同的 deactivation pattern 未套用」。
