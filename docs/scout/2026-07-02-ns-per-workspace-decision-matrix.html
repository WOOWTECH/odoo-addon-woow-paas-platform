核心結論 TL;DR

兩個核心發現＋matrix 打平敘事＋不應跟著 pending 的 P0。完整推理見下方各章節。

  1. 提案（Elmo，2026-07-01 會議議題 5）：一個 PaaS workspace（裡面可放 cloud service / Security Access / Smart Home）只用一顆 k8s namespace，該 workspace 的每個 cloud service type 都灌進這顆 ns；跨 workspace 的 ns 之間網路隔離、同 ns 內自然互通。
  2. 核心發現 ①——marketplace 的 cloud services 其實「已經」這樣做了：部署程式碼從第一版起就是 per-workspace 共用 ns（先是 paas-ws-{workspace.id}，2026-03-01 起改 paas-ws-{md5(slug)[:8]}，粒度從未變過）；live stg 上一顆 paas-ws-stg-86f34bd4 就同時住著 odoo + n8n + 3 個 mcp-server（5 個 release、3 種 type）。
  3. 「每個 service 自己一顆 ns」的印象來自另外兩個地方：agent runtime（per-project 獨立 ns）與 prod 手動搬遷存量（woowtech-odoo、woowtech-n8n 每服務一顆，共約 29 顆、不在 operator 管轄內）——會議是在「per-service」的前提下討論這個提案的，該前提對 marketplace 路徑不成立（§2）。
  4. 核心發現 ②——提案的真正工程 scope 比想像小、也跟想像不同：marketplace cloud services 零工程（已是提案形態）；agent runtime 是唯一要搬的（per-project paas-ws-pa-{hash} → 併入 workspace ns），全部改動與 4 個硬 blocker（§6）都集中在這；SA / SM 完全沒有 k8s 資源（純 Cloudflare tunnel、connector 在使用者硬體/家中），零影響；prod 手動存量正解是收編進 marketplace（收編當下自然落入 workspace ns），不是在手動軌道內另做一次 ns 合併。
  5. 「跨 workspace 網路隔離」現狀並不存在單一保證（隔離三態混雜，§2.3-1）——這是提案的前提配套，也是兩案共同欠的地基。
  6. 13 維 decision matrix：現狀 40 vs 提案 40，總分打平——但分數結構不對稱：提案贏在結構性維度（quota 可控、計費歸屬、擴增性、互通性），現狀贏在風險維度（blast radius、名稱衝突、K8s API 層安全、遷移成本）。打平意味著決策取決於配套是否入 scope、而非粒度本身；會議「pending、不擋 7 月底上線」的決議與本分析一致（Project 先隱藏 → agent per-project ns 成長凍結）。
  7. 但 §7 第 0 段的 6 項 P0 與粒度無關、不應跟著 pending——其中「租戶隔離補鋪」與「PVC 誤標」屬上線前資安/資料安全 gap。
01

名詞與提案定義

workspace＝PaaS 的租戶容器——一個 workspace 裡可以放多個 cloud service（odoo / n8n / mcp-server…各種 type）、Security Access、Smart Home，並可掛 project（agent runtime 的宿主）。

方案一（現狀）

混合粒度
  • Cloud Svcmarketplace cloud services 共用 per-workspace ns
  • Agent每個 project 一顆獨立 ns
  • SA / SM無 k8s 資源
  • 另有prod 手動搬遷存量（per-service ns，§2.1）

方案二（提案）

每 ws 恰好一顆 ns
  • 落點該 workspace 所有工作負載（所有 cloud service type + 所有 project 的 agent runtime pod）同 ns
  • 網路跨 workspace deny、同 ns 內互通
  • 評分前提「跨 workspace deny」的 NetworkPolicy 配套隨提案一起落地（查核確認此前提若抽掉，方案二網路安全分數不成立）

會議語境：Elmo 提案的資安自我說服理由是「同一個 workspace 代表使用者已知這幾個服務在同一區網 / 同一企業」；Eugene 的顧慮是會影響命名方式、效益不一定夠大、「拆開較安全」。會議決議 pending、優先度低、不擋 7 月底上線（待辦 #12）。本文即該評估的執行結果。

2.2 「每服務自己一顆 ns」印象 vs 實作 — 本次分析的關鍵校正

會議前提對 prod 手動存量與 agent runtime 成立，對 marketplace 路徑不成立

印象（會議前提）

✕ 對 marketplace 不成立

「目前每個 cloud service type 有自己的 ns」——印象來源可考：

  • 來源 1prod 上看得到的所有客戶服務（手動搬遷那批）確實每服務一顆 ns
  • 來源 2agent runtime 確實 per-project 一顆 ns
  • 來源 3會議中「service build 時是不同 namespace」的語境是 Hermes MCP（cloud service，會落 paas-ws-*）↔ Hermes Agent 本體（在 eugenechen-hermes，手動軌道）——那兩個確實不同 ns，但推廣到「CS type 之間互相不同 ns」就與程式碼不符

實作（三重驗證）

✓ 自始 per-workspace 共用
  • 程式碼唯一產生點 src/controllers/paas.py:2047，輸入只有 workspace.slug
  • git 歷史31835ff（2026-03-01「refactor: use naming module」）：ns 由 paas-ws-{workspace.id} 改 paas-ws-{md5(slug)[:8]}，粒度自始 per-workspace
  • livehelm list -n paas-ws-stg-86f34bd4＝odoo + n8n + 3 mcp-server，5 release 3 type 同一顆 ns（決定性證據）
含義：提案對 marketplace CS 是「確認並守住現狀」，不是新工程；決策重心因此移到 agent runtime 併入與否（§4–§6）、以及 prod 存量的收編路徑（§7）。

2.3 兩個顛覆直覺的現狀事實

2.3-1租戶網路隔離現狀是「三態混雜」，平台層保證缺席（CS 側）

operator create_namespace 只建 ns + ResourceQuota + registry secret（extra/paas-operator/src/services/helm.py:737-811），全 repo 無任何對 CS 租戶 ns 下 NetworkPolicy 的程式。Live 驗證三態：

① marketplace CS ns 內存在 chart 自帶 per-release NP，但語意等效放行（svc-*-odoo 的 ingress rule 只限 port、不限來源＝任何 ns 都能打 8069；egress allow-all）→ 跨租戶隔離實質缺席；② agent ns 有 per-instance 雙向 default-deny NP（chart 實檔驗證，§5-2），但 11 顆中只有 6 顆有（較舊 5 顆零 NP，chart 版本 drift）；③ prod 手動存量有 15 顆 ns 鋪了 default-deny-external（allow same-ns ingress / deny 跨 ns，約 2026-06-25 統一鋪設），14 顆全裸（全部 5 顆 hermes 系、bnidistrict/changching/linyanshan/lisachuzhu/lyucijyun-odoo、woowtech-n8n、hermes、hermes-mcp-admin、woowhademo）。

「跨 workspace deny」沒有單一保證來源、覆蓋有洞，是兩案共同欠的地基，與 ns 粒度無關。

2.3-2agent→租戶服務互通現狀是 dead path

NP 設計走 namespaceSelector matchLabels woow.tw/workspace-id（design.md:3486-3497），但 CS ns 從未被貼該 label（build_managed_ns_labels 只有 paas-managed=true + env，helm.py:108-129），且 sync-workspaces 端點在生產碼無 caller → project 改綁 cloud service 後 egress allowlist 不同步。修法（貼 label + 接線）與粒度正交。

2.4其他關鍵事實（6 條）
  • 01delete_namespace 全 codebase 唯一生產 caller = agent teardown（agent_runtimes.py:577-586）；operator 連可刪 CS ns 的 API 端點都不存在（namespaces.py 僅 POST create）→ CS 孤兒 ns + quota + registry secret 永存、無 TTL。
  • 02Quota：CS ns 有（max(3×sum(allocated), 8CPU/8Gi/100Gi)、persistentvolumeclaims=10 硬編碼、每次 deploy 重算但刪 service 不縮，cloud_service.py:438-447 + helm.py:770-787）；agent ns 完全無 quota（_ensure_namespace 只 apply label，agent_runtimes.py:81-95）；全 repo 無 LimitRange。Live 佐證：paas-ws-stg-86f34bd4 PVC 已用 6/10（5 個 release）——PVC 上限分食是現在進行式；paas-ws-stg-ad023482 用量全零但殘留 12CPU quota ＝「服務刪光後 ns + quota 永存」的實例。
  • 03project↔workspace 是 M:N（project.workspace_ids 是從 cloud_service_ids 算出的 computed M2M，project_project.py:36-49），且 unbound project 合法（decouple invariant D1）→「per-workspace ns」對跨 ws / unbound project 沒有唯一落點，是提案的 design gap。
  • 04ns 上無任何 workspace/owner label；ws_hash = md5 單向、agent hash = HMAC 刻意反枚舉。但 agent ns 的 workspace ids 其實已持久化在 k8s 端（helm release-state Secret，helm get values 可還原）。
  • 05Odoo 端 ir.config_parameter namespace_prefix 與 operator env NAMESPACE_PREFIX 是兩個獨立配置源、無共同來源——改 ns 模型時的 drift 風險點（live 證實 stg 兩端已同步為 paas-ws-stg-）。
  • 06Cloudflare 命名與 ns 的耦合只有一處：CS 的 MCP subdomain 公式吃 ns 名（generate_subdomain = {release}-{ns 去 paas-ws-}，cloudflare.py:804-816；Odoo 端 reconstruct_mcp_subdomain 跨 repo byte-identical，src/services/naming.py:61-80）——維持 paas-ws-{md5(slug)[:8]} scheme 不動就沒有命名連鎖。docs 內既有「統一命名」分析（naming-env-token plan、L4 reconciler）全部是 prod/stg env-token 軸，per-workspace ns 粒度是新題。
03

各子系統衝擊

若把 agent runtime 併入 workspace ns：改動 100% 集中在 agent runtime，其餘子系統零或幾乎零。

子系統提案衝擊
Cloud Service零工程（已是提案形態）。被動衝擊：quota 被 agent 分食、PVC 誤標面擴大、可能被 agent teardown 整鍋端（§6）
Agent Runtime全部改動集中在這：3 處 ns 推導 lock-step（agent_runtimes.py:61、mcp_invalidator.py:18-22、skill_invalidator.py:22-26）、API contract（reap/resume/status/invalidate/delete 全以 project_hash 單鍵導 ns）、cross-repo chart、DB migration（stored helm_namespace/pod_ws_url 全 stale）、teardown 重寫
Security Access幾乎零。唯一守線：canonical_name 刻意不從 namespace_prefix 推導（security_access.py:207-213，identity-anchor 設計保證），ns 改制不得反向引入耦合
Smart Home零。守線：「刪 ns ≠ teardown 租戶」——CF 資源不在 ns 裡，必須仍走 Odoo unlink guard（否則重演 cf-ns-orphan pitfall）
Cloudflare 整合agent runtime 零 CF 資源 → 併入本身零影響。風險僅在「順手改 ns 命名 scheme」→ MCP subdomain 跨 repo 契約連鎖（§2.4 末條）。別動 paas-ws-{md5(slug)[:8]} 就安全

反證查核的翻盤點

原始打分有 5 處立論被自家查核推翻，本文分數已回填。記錄於此供日後重評時對照。

翻盤 1「agent ns 無 quota → 提案容量失控」方向搞反
無 quota 是現狀的缺口；提案反而讓 agent 落入 marketplace 既有 per-tenant quota 之下。
翻盤 2「NP union 提權」不成立
design.md:3471-3473 的 name-only podSelector 是過時 skeleton；chart 實檔（woow-paas-charts/charts/agent-runtime 0.4.3，自首 commit 起）的 NP podSelector = app.kubernetes.io/name + app.kubernetes.io/instance: {release}，per-instance。同 ns 多 agent 不會互相 union egress。
翻盤 3「同 ns 自然互通」對 agent 不成立
agent chart 是 Ingress+Egress 雙向 default-deny 且無 same-ns allow——合併 ns 後 agent egress 仍只有 TCP 3000/3001（且仍要 ns 貼 workspace-id label 才 match）。連帶「prompt-injection 下 agent 直連租戶 DB」的風險敘事也被推翻（除非 NP 改開）。
翻盤 4「per-release GC 從零重寫」不成立
CS delete_release 已是共用 ns 內的 per-release GC 骨架（helm uninstall + PVC orphan label）；agent 缺的只是 {release}-llm Secret 刪除（operator KubectlService 現無 delete secret 方法）。
翻盤 5auth Secret 撞名後果修正
不是「靜默互踩輪替 key → 間歇 401」，而是固定名撞 Helm ownership → 同 ns 第二個 agent release install 直接失敗。對提案是更硬、但 fail-loud 的 blocker。
翻盤 6「agent ns→workspace 對映僅存 Odoo DB」不成立
workspace ids 持久化在該 ns 的 helm release-state Secret（helm get values 可還原），Odoo 消失後仍可反查（只是可發現性差）。
誤判排除C-scale 把「方案一/方案二」指涉讀反
另有一條 C-scale 查核把現狀讀成提案，該 refuted 屬誤判，已在校準時排除。
06

提案的硬 blockers（缺一不可）

動工前必須解的 4 項，全集中在 agent runtime。點卡片展開細節。

1 · agent chart auth Secret 改 release-scoped 命名硬 blocker

cross-repo woow-paas-charts——否則同 workspace 第二個 project 的 agent 裝不起來（撞 Helm ownership，§5-5）。

2 · delete_runtime 改 per-release teardown硬 blocker

複用 CS delete_release 骨架 + 補 {release}-llm Secret 刪除；delete_namespace 從 agent DELETE 路徑移除，workspace teardown 做成獨立顯式端點（dry-run 列將刪資源 + 確認 token），過渡期給 delete_namespace 加「只准刪 pa- 前綴」型別 guard。

3 · quota 模型統一硬 blocker

公式改 3×sum(CS allocated) + sum(agent 配額)（可啟用 dormant 的 agent_session.quota_override_*）、persistentvolumeclaims=10 參數化、補 LimitRange（否則未宣告 resources 的容器被 admission 拒建）、spawn 路徑加 quota 預檢與明確錯誤回報。

4 · M:N / unbound project 的 pod 落點拍板硬 blocker

plan-gap-stop-and-report 紀律：primary_workspace_id 升格為建立時 snapshot、不隨綁定漂移的 stored 欄位；或禁跨 ws 綁定；unbound project 明訂 fallback（保留 per-project ns？禁用 agent？）。

▲ 三段式：第 0 段先行（資安地基）、第 1/2 段隨會議決議維持 pending

第 0 段與粒度解耦、現狀就該修的 P0（不應跟著 pending）

會議把整個 ns 議題 pending 掉了；本段各項不應跟著 pending——它們與粒度無關，其中隔離補鋪與 PVC 誤標屬上線前資安/資料安全 gap。

  • A補齊租戶隔離的未覆蓋名單（上線前資安 gap）：prod 手動存量的 14 顆全裸 ns（全部 hermes 系、5 顆 odoo、n8n 等，§2.3-1）比照既鋪的 15 顆補 default-deny-external；marketplace 側在 paas-ws-* ns 落地 default-deny + allow-same-ns + 顯式開洞（cloudflared ingress / operator / Odoo↔agent / DNS），並釐清 agent ns 6/11 有 NP 的 chart 版本 drift（舊 spawn 補渲染或 respawn）。開洞前先以 live cluster 釘死 cloudflared shared-tunnel pod 所在 ns。
  • BCS ns 補 woow.tw/workspace-id label（單一來源 build_managed_ns_labels 擴充；值用 raw workspace id，chart values 註解同步修正）——一次修好 MCP dead path、人工反查、NP selector 三件事。prod 手動存量順手補統一 tenant label（收編 marketplace 前的最低治理）。
  • Clist_pvcs orphan 標記加 app.kubernetes.io/instance={release} selector——資料刪除級 bug，今天同 workspace 多 service 就會誤標（releases.py:229-242 + helm.py:1231-1251）；並開 woow-paas-charts 驗證 pvc-cleanup cron 現行版是否檢查 Bound。
  • Dworkspace.slug write guard（identity-anchor，比照 SA canonical_name 的 su-env-exempt-guard pattern）——ns=md5(slug) 但 slug 現可任意改。
  • Esync-workspaces 接線（project 綁定變更 hook 或 drift cron）。
  • Foperator helm install/upgrade 加 --history-max（建議 3–5）。
第 1 段合併前置（§6 四個 blocker）

解決 §6 的 4 個硬 blocker：auth Secret release-scoped 命名、delete_runtime per-release teardown、quota 模型統一、M:N / unbound project 落點拍板。

第 2 段合併本體（把 agent runtime 併入 workspace ns）

new-only cutover：新 spawn 一律落 workspace ns；既有 pa- ns 靠 idle reaper（5 分鐘 cron）+ 30 天 GC 自然 drain，不做 live 搬遷（helm 不支援 release 跨 ns 搬移；接受 /workspace PVC 狀態丟失）。

ns 命名維持 paas-ws-{md5(slug)[:8]} 不動（避免 MCP subdomain / L4 parse 的跨 repo 契約連鎖）。

配一次性存量清點腳本（列 cluster 全部 paas-ws-pa-* 對 agent_session stored hash 取差集），遷移期孤兒不留長尾；rollout design 先寫：Odoo/operator/chart 三方 lock-step 順序、雙 config 來源（ir.config_parameter vs operator env）合流、回滾語意。

提示決策提示 & prod 手動存量的路線

決策提示：做完第 0 段後現狀分數約升至 45（互通性、網路安全、溯源缺口都被修掉），屆時再評第 1、2 段是否仍值得——提案剩下的獨有紅利 = 單一生命週期模型 + quota 統一 + offboarding 可稽核刪除；獨有代價 = blast radius 集中 + Secret 同鍋 + 遷移工程。時程上與會議決議對齊：第 0 段建議併入 7 月底上線前收尾（資安地基）；第 1、2 段維持 pending，等 Project 解除隱藏（agent ns 開始成長）或 prod 存量收編 marketplace 排程時再啟動。

prod 手動存量的路線（不在 matrix scope，但屬同一決策脈絡）：存量手動服務的終局是 marketplace 化（會議議題 3 的 MCP monorepo 已在走）；收編當下自然落入 per-workspace ns，等於提案在存量側的實現路徑。不建議在手動軌道內另做一次 ns 合併（成本花在即將淘汰的軌道）。收編前最低治理：統一 tenant label + 補齊 default-deny-external。
