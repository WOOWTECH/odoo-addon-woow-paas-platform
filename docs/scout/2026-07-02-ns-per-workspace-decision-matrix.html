核心結論 TL;DR

提案（Elmo，2026-07-01 會議議題 5）：一個 workspace 只用一顆 ns、跨 workspace 網路隔離、同 ns 內互通。以下為查核校正後的裁定。

現狀速覽（平台自動部署的命名體系；證據與第四類「prod 手動搬遷存量」見 §3.1）

服務類別namespace粒度
Cloud Service（Odoo / N8N / PG / MCP…）paas-ws-{env}{ws_hash}per-workspace（同 workspace 多個 CS 共用一顆）
agent-runtime（每個 project）paas-ws-{env}pa-{project_hash}per-project（各自獨立）
Security Access / Smart Home無 k8s ns純 Cloudflare（dedicated tunnel，connector 在使用者端）

註：{env} 由 namespace_prefix 設定承載，非程式插值——prod＝空（paas-ws-86f34bd4）、stg＝stg-（paas-ws-stg-86f34bd4）；Odoo 端 ir.config_parameter 與 operator 端 NAMESPACE_PREFIX 為雙配置源（§3.4）。兩套 hash 制度不同：ws_hash＝md5(slug)[:8]（公開可算）、project_hash＝HMAC-SHA256 base32 16 字元（防枚舉）。prod 手動搬遷存量（{客戶}-{服務}，約 29 顆）不在此命名體系。

  1. 核心發現 ① — marketplace 的 cloud services 其實「已經」這樣做了：部署程式碼從第一版起就是 per-workspace 共用 ns（先 paas-ws-{workspace.id}，2026-03-01 起改 paas-ws-{md5(slug)[:8]}，粒度從未變過）；live stg 一顆 paas-ws-stg-86f34bd4 同住 odoo + n8n + 3 個 mcp-server（5 release、3 種 type）。
  2. 「每服務一顆 ns」的印象來自另外兩處：agent runtime（per-project 獨立 ns）與 prod 手動搬遷存量（每服務一顆、約 29 顆、不在 operator 管轄內）。會議是在「per-service」前提下討論的，該前提對 marketplace 路徑不成立。
  3. 核心發現 ② — agent runtime 不能也不應併入（架構層否決）：project 與 workspace 本來就解耦（M:N、unbound project 合法）→ project-scoped 的 agent pod 在 workspace ns 沒有唯一落點；per-project ns paas-ws-pa-{hash} 是解耦的正確體現、不是待收斂的例外。
  4. Security Access / Smart Home 完全沒有 k8s 資源（純 Cloudflare tunnel、connector 在租戶硬體/家中）→ 零影響。prod 手動存量的正解是收編進 marketplace（收編當下自然落入 workspace ns），不在手動軌道內另做一次 ns 合併。
  5. 「跨 workspace 網路隔離」現狀並不存在單一保證（隔離三態混雜）——與粒度無關的共同地基。
  6. 13 維 decision matrix（評的是「連 agent runtime 都併入」的延伸方案）：現狀 40 vs 提案 40，總分打平——提案贏在結構性維度（quota、計費歸屬、擴增性、互通性），現狀贏在風險維度（blast radius、名稱衝突、K8s API 層安全、遷移成本）。
  7. 建議結論：維持混合粒度——工程面打平＋架構面解耦否決 → 提案改讀為「確認並守住 CS 現狀＋補第 0 段配套」，與會議「pending、不擋 7 月底上線」一致。但 §7 第 0 段的 P0 與粒度無關、不應跟著 pending（含新增的 agent per-project ResourceQuota 項）。

§3.2 「每服務一顆 ns」印象 vs 實作（關鍵校正）

前提對 prod 手動存量與 agent runtime 成立，對 marketplace 路徑不成立。印象來源可考：① prod 上看得到的所有客戶服務（手動搬遷那批）確實每服務一顆 ns；② agent runtime 確實 per-project 一顆 ns；③ 會議中「service build 時是不同 namespace」的語境是 Hermes MCP（cloud service，落 paas-ws-*）↔ Hermes Agent 本體（在 eugenechen-hermes，手動軌道）——那兩個確實不同 ns，但推廣到「CS type 之間互相不同 ns」就與程式碼不符。

含義：提案對 marketplace CS 是「確認並守住現狀」，不是新工程；決策重心因此移到 agent runtime 併入與否與 prod 存量的收編路徑。

§3.3 兩個顛覆直覺的現狀事實

事實 ①租戶隔離現狀是「三態混雜」，平台層保證缺席（CS 側）

operator create_namespace 只建 ns + ResourceQuota + registry secret（extra/paas-operator/src/services/helm.py:737-811），全 repo 無任何對 CS 租戶 ns 下 NetworkPolicy 的程式。Live 驗證三態：

① marketplace CS ns

chart 自帶 per-release NP，但語意等效放行（svc-*-odoo ingress rule 只限 port、不限來源＝任何 ns 都能打 8069；egress allow-all）→ 跨租戶隔離實質缺席

② agent ns

有 per-instance 雙向 default-deny NP（chart 實檔驗證），但 11 顆中只有 6 顆有（較舊 5 顆零 NP，chart 版本 drift）

③ prod 手動存量

15 顆鋪了 default-deny-external（約 2026-06-25 統一鋪設），14 顆全裸（5 顆 hermes 系、多顆 odoo、woowtech-n8n 等）

「跨 workspace deny」沒有單一保證來源、覆蓋有洞，是兩案共同欠的地基，與 ns 粒度無關。

事實 ②agent → 租戶服務互通現狀是 dead path

NP 設計走 namespaceSelector matchLabels woow.tw/workspace-id（design.md:3486-3497），但 CS ns 從未被貼該 label（build_managed_ns_labels 只有 paas-managed=true + env，helm.py:108-129），且 sync-workspaces 端點在生產碼無 caller → project 改綁 cloud service 後 egress allowlist 不同步。修法（貼 label + 接線）與粒度正交。

§3.4 其他關鍵事實

aCS 孤兒 ns 永存、無 TTL

delete_namespace 全 codebase 唯一生產 caller = agent teardown（agent_runtimes.py:577-586）；operator 連可刪 CS ns 的 API 端點都不存在（namespaces.py 僅 POST create）→ CS 孤兒 ns + quota + registry secret 永存、無 TTL。

bQuota：CS ns 有、agent ns 完全無

CS ns 有（max(3×sum(allocated), 8CPU/8Gi/100Gi)、persistentvolumeclaims=10 硬編碼、每次 deploy 重算但刪 service 不縮，cloud_service.py:438-447 + helm.py:770-787）；agent ns 完全無 quota（_ensure_namespace 只 apply label，agent_runtimes.py:81-95）；全 repo 無 LimitRange。Live 佐證：paas-ws-stg-86f34bd4 PVC 已用 6/10（5 release）；paas-ws-stg-ad023482 用量全零卻殘留 12CPU quota ＝「服務刪光後 ns + quota 永存」的實例。

cproject ↔ workspace 是 M:N（＝不併入的架構理由）

project.workspace_ids 是從 cloud_service_ids 算出的 computed M2M（project_project.py:36-49），且 unbound project 合法（decouple invariant D1）→「per-workspace ns」對跨 ws / unbound project 沒有唯一落點——這不是待補的 design gap，而是 agent runtime 不併入的架構理由。

dns 無 workspace/owner label，但 agent→ws 對映其實可還原

ns 上無任何 workspace/owner label；ws_hash = md5 單向、agent hash = HMAC 刻意反枚舉。但 agent ns 的 workspace ids 其實已持久化在 k8s 端（helm release-state Secret，helm get values 可還原）。

enamespace_prefix 兩個獨立配置源 → drift 風險 評估 skip

Odoo 端 ir.config_parameter namespace_prefix 與 operator env NAMESPACE_PREFIX 是兩個獨立配置源、無共同來源——改 ns 模型時的 drift 風險點（live 證實 stg 兩端已同步為 paas-ws-stg-）。

→ 評估 skip（2026-07-02 triage）此分離是刻意的安全邊界（operator 的 validate_namespace 用自家 prefix 當授權白名單，不可讓 Odoo 決定它能管哪些 ns），失敗 fail-loud（HTTP 400）非 silent，非 defect。details＝follow-ups.md F-ENV-8（fold 進 prod-release SOP §6.4）。
fCloudflare 命名與 ns 的耦合只有一處 評估 skip

CS 的 MCP subdomain 公式吃 ns 名（generate_subdomain = {release}-{ns 去 paas-ws-}，cloudflare.py:804-816；Odoo 端 reconstruct_mcp_subdomain 跨 repo byte-identical，src/services/naming.py:61-80）——維持 paas-ws-{md5(slug)[:8]} scheme 不動就沒有命名連鎖。docs 內既有「統一命名」分析全部是 prod/stg env-token 軸，per-workspace ns 粒度是新題。

→ 評估 skip（2026-07-02 triage）invariant 提醒非 defect——兩式已驗 byte-identical + golden test 釘死，且 consumer（L4 reconciler）現為 dry-run（reconcilable 恆 False），即便漂移最壞只誤列「疑似孤兒」報表、不自動刪。details＝follow-ups.md F-NAME-1（跨 repo contract test fold 進 F-ENV-2 自動刪除 graduation）。

反證查核的翻盤點（打分校正記錄）

原始打分有 5 處立論被自家查核推翻，本文分數已回填。記錄於此供日後重評時對照。

1「agent ns 無 quota → 提案容量失控」方向搞反

無 quota 是現狀的缺口；提案反而讓 agent 落入 marketplace 既有 per-tenant quota 之下。

2「NP union 提權」不成立

design.md:3471-3473 的 name-only podSelector 是過時 skeleton；chart 實檔（woow-paas-charts/charts/agent-runtime 0.4.3，自首 commit 起）的 NP podSelector = app.kubernetes.io/name + app.kubernetes.io/instance: {release}，per-instance。同 ns 多 agent 不會互相 union egress。

3「同 ns 自然互通」對 agent 不成立

agent chart 是 Ingress+Egress 雙向 default-deny 且無 same-ns allow——合併 ns 後 agent egress 仍只有 TCP 3000/3001（且仍要 ns 貼 workspace-id label 才 match）。連帶「prompt-injection 下 agent 直連租戶 DB」的風險敘事也被推翻（除非 NP 改開）。

4「per-release GC 從零重寫」不成立

CS delete_release 已是共用 ns 內的 per-release GC 骨架（helm uninstall + PVC orphan label）；agent 缺的只是 {release}-llm Secret 刪除（operator KubectlService 現無 delete secret 方法）。

5auth Secret 撞名後果修正

不是「靜默互踩輪替 key → 間歇 401」，而是固定名撞 Helm ownership → 同 ns 第二個 agent release install 直接失敗。對提案是更硬、但 fail-loud 的 blocker。

6「agent ns→workspace 對映僅存 Odoo DB」不成立

workspace ids 持久化在該 ns 的 helm release-state Secret（helm get values 可還原），Odoo 消失後仍可反查（只是可發現性差）。

7C-scale 查核把「方案一/方案二」指涉讀反 → 誤判排除

另有一條 C-scale 查核把「方案一/方案二」指涉讀反（把現狀讀成提案），該 refuted 屬誤判，已在校準時排除。
