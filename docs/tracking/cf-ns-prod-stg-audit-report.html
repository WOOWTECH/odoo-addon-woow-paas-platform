問題 1 · 所有產生物（ns + CF）可否區分 prod / stg?

部分可靠

部分可靠,無單一權威欄位。 K8s namespace 靠名稱前綴可靠區分（paas-ws- vs paas-ws-stg-,唯歷史 id 命名 ns 例外）;Cloudflare 物件全部無法靠自身 name / comment / tag 區分 env,唯一隱含線索是 DNS content 指哪條 shared tunnel,且只對走 shared tunnel 的 CloudService route 有效。dedicated tunnel（SA / SmartHome）連這條線索都沒有,只能靠帶外事實「prod 平台 Odoo 未裝 CloudService / SA / SmartHome model → 所有 paas-cs/sa/sm 資源都屬 stg」反推。

問題 2 · stg 刪除後 CF 孤兒會不會產生、能否找到並刪除?

會 · 全靠手動

會變永久孤兒;能找到並刪除,但 100% 靠手動帶外操作,無任何自動機制。 dev-sandbox destroy 走 helm uninstall + kubectl delete ns,完全不經 Odoo unlink → stored id 連同 Odoo DB 一起蒸發;operator 又無帳號級 list-all 反向 GC → 失去 DB 反參照的 CF 資源無任何 code path 能再發現。

額外 · CF API 有沒有 description / name / comment / tag 可辨識?

幾乎沒有

tunnel 只有 name（無 description / metadata 欄位）;DNS 有 name / content / optional comment（comment 寫 canonical name 作 traceability,非 env tag）;Access app payload 連 tags / metadata 欄位都沒有;Access policy 只有 name（{canonical_name}: {policy_name}）。

  1. CF 可辨識 env 的結構化欄位數:0 — tunnel / DNS / Access 的 name、comment、tag 一律 hash 格式,零 env 標記。
  2. 唯一 env 線索:1 條(隱含) — DNS 的 content 指向哪條 shared tunnel（stg 55953bfa / prod 328c3a28）。
  3. 帳號級反向 GC code path:0 — operator 無 list-all-tunnels / apps / policies,孤兒失去 stored id 後無法被任何 code 發現。

▲ 逐物件「能否分 env」決策樹:只有 ns 前綴與 shared tunnel id 可靠,其餘退回帶外反推

1 · K8s namespace可靠(單一例外)

靠什麼: namespace 名稱前綴。prod 用裸 paas-ws-、stg 用 paas-ws-stg-,由 operator NAMESPACE_PREFIX env / Odoo Settings ir.config_parameter['woow_paas_platform.namespace_prefix'] 顯式設定（config.py:19、res_config_settings.py）。prod 值在 cross-repo Fleet values-prod.yaml 的 namespacePrefix,promote 時列為「prod 專屬、不可被 stg 覆蓋」。

是否可靠: 對新資料可靠,對歷史資料不可靠。operator 對任何 ns 名強制 startswith(namespace_prefix)（helm.py:79-84）。但 ① ns 物件上完全無 env / owner / TTL 的 label / annotation,唯一 label 是 paas-managed: "true";② 舊孤兒 ns 曾以 id 命名（paas-ws-1/5/253）,其前綴與 prod 裸 paas-ws- 直接相撞,純前綴在歷史資料上會誤判。

正式 pattern: 辨識性缺口已立 pattern docs/decisions/patterns/external-resource-env-token-naming.md,明文禁止從 namespace_prefix 隱式推 env。

2 · cf-tunnel不可靠(自身欄位無 env)

tunnel name 是 hash 格式（SA paas-sa-…、SmartHome paas-sm-…）,不帶任何 env 字樣。

shared tunnel 本身是 prod / stg 各一條固定 id（prod 328c3a28 / stg 55953bfa）,這兩條 id 是已知常數可分;但 dedicated tunnel（每 service 一條）名稱純 hash,無法從 name 判 env,只能靠帶外事實反推。

3 · cf-dns部分可靠(唯一靠 content)

唯一可用線索是 content（CNAME target = {tunnel_id}.cfargotunnel.com）。name / comment 都是 hash,不帶 env。

對走 shared tunnel 的 CloudService route 可靠;對 dedicated tunnel 的 DNS,content 指專屬 tunnel id,無法直接對應 prod / stg。base domain 兩環境完全相同,hostname 本身無法區分。

4 · cf-access app / policy不可靠

app name = caller 傳的 app_name;policy name = {canonical_name}: {policy_name}。皆 hash 格式,無 env。Access app payload 連 tags / metadata 欄位都沒有。

prod / stg 共用同一 CF account + zone,Access 物件無任何 env tag。判孤兒歸屬只能看 CF app 實際引用的 domain / destinations（但 base domain 又相同）→ 實務上仍須靠「prod 平台 Odoo 無 SA model」反推。

風險與缺口

兩類:無法可靠區分 env 的物件（紅）與 無法被反向發現的物件（紅）。此即 cf-ns-orphan-no-account-gc.md pitfall 的核心。

無法可靠區分 env 的物件
  • 所有 CF 物件的自身 name / comment / tagtunnel name、DNS name / comment、Access app / policy name 全是 hash 格式,零 env 標記。Access app payload 連 tags / metadata 欄位都不存在。
  • dedicated tunnel(SA / SmartHome)的 DNScontent 指向專屬 tunnel id,無法直接對應 prod / stg。
  • hostname / base domainprod / stg 共用 woowtech.io,hostname 完全無法區分。
  • 歷史用 id 命名的 namespacepaas-ws-1/5/253 前綴與 prod 撞,前綴辨識失效。
  • 唯一可靠信號鏈「DNS content 指哪條 shared tunnel」+ 帶外事實「prod 平台無 SA model」 — 沒有任何單一、結構化、自證歸屬的 env 欄位。
無法被反向發現的物件
  • 失去 stored id 的所有 CF 資源operator 無 list-all-tunnels / apps / policies,stored id 蒸發即永久失蹤。
  • 繞過 Odoo unlink 刪除的租戶 namespace無 owner / TTL / 反向 GC。
  • best-effort cleanup 漏掉的 DNSper_page 截斷、cascade 失敗只 warning。
  • pitfall 核心此即 docs/tracking/pitfalls/cf-ns-orphan-no-account-gc.md pitfall 的核心。

A · 唯讀 / 手動對帳方法（不動 code,可立即做）
  1. 定期帳號級對帳腳本（帶外）: 用 CF API（per_page=500 或分頁）列出全部 tunnel / DNS / Access app / policy,與 stg Odoo cloud_service / security_access / smart_home 的 stored id 取差集,dry-run 列出孤兒候選。判 env 用「DNS content = shared tunnel id」+「paas-cs/sa/sm 前綴 ⇒ stg」雙重條件。
  2. namespace 對帳: kubectl --context woow-k3s get ns -l paas-managed=true ↔ stg Odoo record 取差集,找出無主租戶 ns。
  3. Access policy 判孤兒一律以 CF 為準: GET /access/apps/{id}/policies,不信 Odoo DB 白名單,靠 409 in-use 兜底。
  4. 清除遵守順序: route 三處（DNS + ns + ingress rule）一起;Access 先脫鉤再刪;tunnel cascade 後手動驗 DNS。
  5. 銷毀前置 teardown 紀律: 在跑 k8s-dev-sandbox destroy / stg DB 重置前,先透過 Odoo 觸發 CF teardown（讓 stored id 還在時就清遠端）,再銷毀沙盒,避免製造新孤兒。這是避免製造新孤兒最有效的一步。
