結論速覽

兩問各一段濃縮。完整推理見下方各章節。

  1. 問 1(CF 命名加 env token):可行,但要分清欄位語義。若 token 加在 naming.py 單一根(make_*_subdomain 前綴層),對 SA 內部 tunnel name / DNS comment / Access app name 是零破壞且 create↔delete 天然對稱(這些值 immutable stored、刪除靠 stored id 不重算)。最關鍵 caveat:使用者自填的 SA route public hostname(subdomain_prefix)不該也不能注 token —— 那是對外 URL,env 區隔要靠 per-env paas_domain(security_access.py:851-857、:918-926)。能安全注 token 的只有平台自產的 canonical_name 與 CloudService/SmartHome 自產的 subdomain。
  2. 問 2(ns label + PAAS_ENV):不是「同解很多問題」,而是「真解辨識性、只 enable 反向 GC、完全不解孤兒不再產生」。這三件事是同一條「可辨識性」主線,真正解掉的是「一眼辨 env / kubectl -l 查詢」;對孤兒治理整類(能被發現、不再產生、自動回收)多半只是 enabler 或完全不解。最關鍵 caveat:label value 不可用帶尾 dash 的 namespace prefix 字面(paas-ws-stg- 非法),必須用乾淨 token value=stg / value=prod(helm.py:90 regex 要求英數開頭結尾),否則整批 label 被 k8s atomic 拒、重蹈 #208 教訓。
01

能解 / 不能解矩陣

一句話總結:辨識性整類(P1a/P1b solves、P3 部分)是真解;孤兒治理整類(P2a/P2c enabler、P2b/P5 no)token+label 多半幫不上。「讓孤兒較好辨認 ≠ 讓孤兒被發現 / 不再產生 / 自動回收」。

項目判定理由(附證據)
P1a 辨識性
(CF 物件一眼辨 prod/stg)		 solves(tunnel/DNS/policy) partial(app name) naming.py 是 tunnel name / DNS comment / Access policy name 的單一根,注 token 一改全到位且 create/delete 對稱(naming.py:19,24,29;tunnel security_access.py:368、DNS comment :547、policy name cloudflare.py:1322)。例外:Access app name 主路徑 = 使用者自填 subdomain_prefix(security_access.py:1203,非 canonical_name),不該注 token —— 見 public-URL 專節。目前 CF 可辨識 env 的結構化欄位數 = 0。
P1b ns 可查詢
(kubectl -l env=stg)		 solves 目前唯一 ns label 是 paas-managed=true,無 env(helm.py:683-684)。加 env label 即可查詢化;label 屬純 metadata、不參與反查、零破壞。
P2a 孤兒可發現
(反向 GC reconciler)		 partial(token 只是 enabler) 真正缺的是 operator 無任何 list-all-tunnels/apps/policies(cloudflare.py:399,439 僅單-id 列舉)。env token 只在「已有 reconciler」後讓它判 env 更乾淨,自身找不回一筆孤兒。
P2b 孤兒不再產生 no(完全不解) 根因是銷毀繞過 Odoo unlink(destroy.sh / DB 重置 / 手動 kubectl delete 不經 ORM),stored id 蒸發(subscription_lifecycle_cron.py:118 record-driven)。與命名/標籤正交;要堵須加前置 Odoo teardown 或 SmartHome 補 fail-loud guard(smart_home.py:202 無條件 unlink)。
P2c ns TTL 自動回收 partial(label 只是 enabler) ns 加 owner/env label 是「讓對帳 cron 能掃」的前置,但 label 不會自動過期;自動回收仍須另做 TTL annotation + 對帳 cron。
P3 跨環境碰撞 partial prod/stg 共用同一 CF account+zone+base domain(woowtech.io,非 *.stg 設計)。token 注在 traceability 欄位解的是「碰撞後能辨認」,不解「不碰撞」。對外 hostname 真正分環境靠 per-env paas_domain(res_config_settings.py:20-22)。但若 token 併入 hash 種子/前綴(改變實際命名空間),則對 CloudService/SmartHome 自產 subdomain 能結構性保證跨環境零碰撞 —— 這是 token 比 label 多出的硬價值。
P4 reconciler enabler solves(作為 enabler) 共用 account list-all 撈出 prod/stg 混在一起,目前只能靠「DNS content 指哪條 shared tunnel」脆弱反推(dedicated tunnel/Access 連這線索都沒)。顯式 PAAS_ENV stamp 後 reconciler 可直接按 env 欄位過濾。前提是先補 list-all(見 P2a)。
P5 既有回填 no 且引入新風險 canonical_name immutable、ns 名已固定 → 注入只對新 record 生效,DB 新舊混用。更糟:reconciler 必須同時認得「有 token」與「無 token」雙格式,否則舊 record 反成辨識不到的孤兒(external-resource-env-token-naming.md:40-41)。歷史 id 命名 ns(paas-ws-1/5/253)前綴與 prod 裸 paas-ws- 直接相撞,token 無法回頭救。

03

public URL vs 純 traceability 專節

關鍵分水嶺:使用者的 paas-stg-sa- 到底指哪個欄位?——對外 hostname 不該注 token,只有內部標籤可以。

✓ 安全注 token

SA canonical_name

內部 tunnel name / DNS comment / Access policy name

canonical_name 在 SA 路徑絕不對外曝光成 hostname。註解一字不差:「canonical_name is only the tunnel's CF identity (its name), never surfaced as the hostname」(security_access.py:133-135)。只當三種純 traceability:CF tunnel name(:368)、DNS comment(:547)、Access app/policy name(:594-595),皆不參與 routing / 反查。

結論:注 env token 對 SA 零破壞、不改任何 public URL,只改 CF dashboard 內部標籤。
✕ 不該注 token

SA subdomain_prefix

public hostname(使用者自填)

對外 hostname = {subdomain_prefix}.{paas_domain}(:918-926)。subdomain_prefix 是使用者自填、required、全平台扁平 first-come-first-served、create 後 immutable(:851-857、UNIQUE :838-840)。pattern doc 明確劃為「不適用」env-token 注入(external-resource-env-token-naming.md:12):env 區隔該靠 per-env paas_domain。

連帶:Access app name(display name)主路徑就是這個 subdomain_prefix(:1203、teardown :595 僅 prefix 空時 fallback canonical_name)→ 同樣不該注 token。Access 物件能「穩定帶 env」的只有 policy name({canonical_name}: …,cloudflare.py:1322),不是 app name —— 早前對照表把 app name 標成 canonical 根屬不精準,已於 external-resource-env-token-naming.md:28 與 P1a 同步校正。
△ 介於兩者之間

CS / SM subdomain

平台自產 hash,但對外

它們的 subdomain 本身就是 make_*_subdomain 算出的 hash,且直接拼成對外 hostname(cloud_service.py:984、smart_home.py:281)。因平台自產(非使用者自填),是 pattern doc 適用注 token 的候選。

但動它＝改使用者 URL,要慎(CloudService legacy shared-tunnel 路徑前述 A 類已驗證走 stored 值,對稱成立)。

給使用者的直接回答

  • 若 paas-stg-sa- 指 SA route 對外 subdomain,不該注 token(那是使用者自填 hostname,env 靠 paas_domain)。
  • 只有 SA 的 canonical_name(內部 tunnel name / 標籤)才是可安全注 env token 的對象,且不改任何對外 URL。
04

PAAS_ENV 是什麼角色

PAAS_ENV 是「單一顯式 env 來源原語(primitive)」,不是功能本身。它解鎖三件下游,但本身不建 reconciler、不加 ns TTL、不堵孤兒產生。

它解鎖三件下游:① ns label paas.woowtech.io/env;② CF naming token;③ 未來 reconciler 按 env 過濾。

現況事實(grep 證實):operator 全域無 PAAS_ENV / DEPLOY_ENV(config.py 0 命中,只有 namespace_prefix="paas-ws-" @ :19)。

誠實分類「同解很多問題嗎」 —— 真解:P1a 辨識、P1b ns 查詢、P4(reconciler env 過濾 enabler,定位精準)。只是 enabler:P2a(要先有 list-all reconciler)、P2c(要先有 TTL+對帳 cron)。完全不解:P2b(根因繞過 ORM)、P5(不回填 + dual-format 負擔)。

守則設計守則(pattern doc:17 + verify confirmed)

● Odoo 端 env token 來源用既有 config_parameter woow_paas_platform.namespace_prefix(已帶 stg 慣例 paas-ws-stg-,res_config_settings.py:28-33)或新增專用 config_parameter,在 naming.py 單一根 stamp。

● operator 端若也要帶 env,必須在 cross-repo paas-app-bundle-cd Fleet CD values 新增顯式 PAAS_DEPLOY_ENV 注入 operator Deployment env(config.py:76-77 註解明示 operator 自身 Deployment env 住那裡、非本 repo chart 渲染)。

● 禁止在 operator 寫 namespace_prefix.removeprefix("paas-ws-") 靠「prod=空字串」隱式推導(pattern 守則 2)。

兩個注入機制 × 各 CF / k8s 欄位歸屬(逐欄位該走哪條)

env 標記其實只收斂成兩個注入機制,不是「每個欄位各引入一次 PAAS_ENV」。判斷一個欄位該走哪條,就看「它在 Odoo 算還是 operator 算」。

06

風險與前置

落實時最致命的兩個雷:immutable guard 測試別 su 豁免 與 label value 別帶尾 dash。預設展開第一條,其餘點開看細節。

1immutable canonical_name guard(create 首算、測試別 su 豁免)

env token 只能在 create 的 _generate_canonical_name 內算進去,不能事後 write 注入 —— create() 對所有人(含 superuser)pop 掉 caller 傳入值(security_access.py:221-237),write() guard 用 sa_internal_identity_write context-key 鎖死(:248-253),刻意不放行 env.su(因 TransactionCase 是 su env,放行會讓 deny 分支跑不到 → 假綠)。

守線測試紀律:新增 env-token 邏輯時不可把 guard 改成 not env.su 形態,否則同時破壞既有守線(su-env-exempt-guard-false-green.md:46-67)。subdomain_prefix 同屬 immutable anchor,rename = delete+recreate。

2既有 record 不回填 → dual-format reconciler

canonical_name immutable、ns 名已固定 → 注入只對新 record 生效,DB 新舊命名永久混用。任何未來 reconciler / 孤兒清理器必須同時認得「有 env token」與「無 env token」兩種格式,否則舊 record 反成辨識不到的孤兒(external-resource-env-token-naming.md:40-41)。

3label value 合法性(stg 尾 dash 非法、用 value=stg)

helm.py:90 regex ^(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?$ 要求英數開頭結尾。實測:stg/prod 合法,paas-ws-stg-/stg-(尾 dash)非法,paas-ws-stg(無尾 dash)合法。

label value 必須用乾淨 env token(stg/prod),不可把 namespace_prefix 字面當 value,否則 k8s atomic 拒整批(重蹈 #208 colon-orphaned-at:單一 bad value 靜默丟整批、錯誤被吞成 WARNING、74 天沒生效)。
