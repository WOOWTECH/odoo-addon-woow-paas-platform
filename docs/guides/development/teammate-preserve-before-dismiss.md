## 0. 這份文件為什麼存在

2026-08-23，#289 收尾。派工者照範本保全了一位 teammate 的產出（canvas note），
dismiss **之前**做完範本要求的搬位探針——第三方讀回、驗行數（126）、驗 6 個內容鍵、
配陰性對照（`ZZZ_NOT_PRESENT` → 0），**全部通過**。然後 dismiss，兩份 note 就都讀不到了：

```
maestri: No connection to note 'dev-289-docs 保全原文'.
Connect to the note first in the canvas.
```

共 125 + 142 行，其中的原始輸出片段永久失去。

⇒ **一份教人保全的東西，自己沒有被保全。** 範本只活在派工訊息與協調者的 context 裡，
`docs/` 與 `.claude/` 全樹 grep 零命中。本文終止這件事。

🔑 **保全規則最常被寫在「正在派工」的那則訊息裡，而那正是壽命最短的載體。**

---

## 1. 什麼時候要跑這套

派工者（leader／協調者）準備 **dismiss 一位 teammate** 之前。
不是「任務做完時」，是「**人要消失之前**」——這兩個時間點可以差很遠，
而只有後者是不可逆的。

---

## 2. 判準：什麼東西要保全

> **這件事如果只活在我們的對話裡，明天就沒了。** `[#798][#289]`

兩份實例逐字相同的一句，這是協定的核心判準。

**已經有載體的不要重抄** `[#798][#289]`——已經在 PR body、doc、issue 留言裡的東西，
重抄會製造第二份，**之後兩份會漂**。需要指涉時**指向那則留言／那份 doc**，不要把內容搬過來。

派工者列出自己認為「無載體」的候選清單，並明講 **「你自己再增刪」** `[#798][#289]`。
兩份實例的候選清單裡，逐字相同的最後一格是：

> **你自己覺得下一個人會撞、而目前沒地方記的任何事。** `[#798][#289]`

### 兩份實例實際列進候選的東西（照抄它們的類型，不是照抄內容）

- **量測的來龍去脈**：哪些探針試過但被換掉、**為什麼換**。`[#798]`
- **腳本的「要解決什麼、判準形狀、已知盲區」**——腳本本體在 scratchpad 會被清掉，
  至少要把這三樣留下來。`[#798]`
- **真因的追查過程**——結論可能已經有載體了，但「**怎麼追到的**」通常沒有。`[#798]`
- **探針自身的失效與抓到它的手法**（例：`git grep -E` 不支援 `\b`、靜默回 0，
  而抓到它的是「同一次執行裡有另外 4 個通過」＝探針的陽性對照）。`[#289]`
- **判準本身的演進**（例：CI 綠的判準從「PR 頁面有 ✓」換成查 commit statuses 的完整推導）。`[#289]`
- **已有載體的環境事實**：**不重抄，只指向那則留言**。`[#798]`

## 3. 四步協定

> 🔴 **順序不要換。** `[#289]`
>
> 原本是三步「保全 → 驗 → dismiss」；**2026-08-23 的事故補上了第 2 步**。`[2026-08-23]`

### 步驟 1 — 保全（**先於 dismiss**）`[#798][#289]`

teammate 依 [§2](#2-判準什麼東西要保全) 把無載體的事實寫出去。

**落點** `[#798][#289]`：canvas note，`maestri note create --name "<名字>"`，
**回報實際被指派的名字**（`note create` 的回應會印出精確名字，`--name` 之後仍可能被改寫）。

**第二落點（檔案型產物）** `[#798]`：repo 旁的 sibling 工作目錄（`wt-<n>-workorder/` 這類）。
⚠ 它**在 worktree 之外**，清 worktree 不會動到它；但它**也不在 git 裡**，
所以**該進 repo 的東西不要放這裡**。

### 步驟 2 — 移轉到派工者名下 `[2026-08-23]`

🔴 **這一步是 2026-08-23 事故補上的，兩份實例都沒有。**

> **保全的落點必須掛在「不會跟著被清掉的東西」上。**
> teammate 建的 note 與 teammate 同生共死 ⇒ **它不是保全，是暫存。**

合格落點（依附對象不會因 dismiss 消失）：

| 落點 | 依附於 | 撐得過 dismiss？ |
| --- | --- | --- |
| **repo 內檔案**（commit／PR） | git | ✅ |
| **issue 留言** | Gitea 伺服器 | ✅ |
| **派工者自己建的 canvas note**（`maestri note create` 由派工者執行） | 派工者的節點 | ✅（派工者還在的期間） |
| **teammate 建的 canvas note** | **teammate 的節點** | ❌ **節點消失 ⇒ 沒有邊可以走到它** |
| scratchpad | session 目錄（有 TTL） | ❌ |

⚠ **note 本身應該還在畫布上**——失敗訊息說的是「沒有連線」不是「不存在」。
但派工者已經沒有邊可以走到它，這對收尾而言與消失等價。

⚠ **本表只涵蓋「保全落點合不合格」這一個問題**，不是通用的載體持久性排序——
不要拿它當「什麼東西該放哪」的通用表用。

### 步驟 3 — 驗（搬位探針）`[#798][#289]`

🔴 **必做。保全完之後實跑一次「從新位置讀得回來」，不要只確認「我寫出去了」。** `[#798][#289]`

- **note**：teammate 自己 `maestri note read "<名字>"` 讀一次，**回報行數**。`[#798][#289]`
- **檔案**：`wc -l` ＋ `realpath` 貼出來，確認它在 sibling 目錄而**不在 scratchpad**。`[#798]`
- **派工者獨立再讀一次當第三方複驗** `[#798][#289]`
  ⇒ 所以名字與路徑要給**精確值**，不要「大概叫…」。`[#798][#289]`

第三方複驗實際長什麼樣，見 [§6](#6-第三方複驗長什麼樣798-實例)。

### 步驟 4 — dismiss

前三步都通過才做。

**清理與 dismiss 的時序** `[#798]`：**不要清 worktree、不要刪遠端分支**，
直到合併後的 backstop（develop push 觸發的全套測試）綠。
⚠ 那一趟往往正好補上 teammate 未驗清單裡的格子（PR CI 不含模組測試、合併後的樹沒重跑），
紅了要回頭看。

**刪任何東西之前先驗前提** `[#289]`：

- `git ls-remote origin refs/heads/<branch>` 取**當下**指向——**不要用你記得的那顆 sha**
  （走 update-branch 合併時，遠端 head 會變成你沒看過的 commit；照舊 head 驗過就刪＝成功但無警告）。
- `git merge-base --is-ancestor <當下 head> origin/develop` 應 rc=0。
- 🔴 **陰性對照必須是「今天確實不成立」的標的**——挑一條**現在還沒併**的分支 tip 驗它 rc=1，
  挑之前先 `ls-remote` 確認它真的還沒併。#798 收尾時拿一顆早就併進 develop 的 sha 當對照，
  rc 回 0，**那個對照零鑑別力，而它差點被用來放行刪除**。
- 刪遠端分支：刪前 `ls-remote` 1 行 → 刪後 0 行，**並附陽性對照**（例：develop 仍回 1 行，
  證明查法還會回話）。
- `git worktree remove`：驗 rc、目錄不存在、且**不在 `git worktree list` 裡**（三項都要）。

**資源歸還** `[#289]`：收尾後報一次 `df -k`（含 mount 那行）與起用前配對。
⚠ 用 `df -k` **不要 `df -h`**——格式化值兩端各自四捨五入會製造偽陰性。
判準看 **Avail** 那一欄（會變的那欄），不要看 sealed volume 那行的 Used（它恆定、可重放）。

**收尾回報** `[#289]`：謝三件**具體**的事——具體到可以指出是哪一次判斷、哪一個輸出。

## 4. 🔴 為什麼「驗過了」還是會丟

**這是本文最重要的一節。** `[2026-08-23]`

搬位探針問的是「**此刻**從新位置讀得到嗎」；
保全存在的理由是「**撐過 agent 消失那一刻**」——**而那一刻正是探針沒有涵蓋的事件。**

⚠ 更糟的是：

> **在 dismiss 之前，「會活下來的 note」與「不會活下來的 note」輸出完全不可區分。**
> 兩者都回得出行數、都通得過內容存在性檢查、都配得上陰性對照。

⇒ **dismiss 前要驗的不是「我讀得到」，是「我 dismiss 之後還讀得到」。**
那件事無法在 dismiss 之前直接量到 ⇒ **唯一誠實的驗法是先把內容搬到自己的載體上、驗過，再 dismiss**
（＝[步驟 2](#步驟-2--移轉到派工者名下-2026-08-23) 存在的理由）。

這與「我剛剛還查過它存在」是同族，但**多一層**：
那條的失效是**時間流逝**，這條的失效是**你自己執行的那個動作**。

> 同族但不同機制的另一例：[assertRaises 的 savepoint 回捲](../../tracking/pitfalls/odoo-assertraises-savepoint-rollback.md)
> ——**都是「探針測到的世界不是你以為的那個世界」**。內容看該 doc，本文不重述。

## 5. 探針自己會壞

零命中先假設探針壞了，不要先假設「東西不在」。實際踩過的兩種：

- **ERE 裡的 `\|` 是字面反斜線**，不是 alternation ⇒ 三個假 0。`[#798]`
- **`git grep -E` 不支援 `\b`，靜默回 0** ⇒ 29 個裡誤報 25 個 MISS。`[#289]`

⇒ 所以 [§6](#6-第三方複驗長什麼樣798-實例) 的陰性對照那一格不是形式主義：
它是**用來證明這把尺今天還會回話**的那一格。

## 6. 第三方複驗長什麼樣（#798 實例）

### 先講定「在哪棵樹／哪個 ref 上量」`[2026-08-23]`

🔴 **複驗開始之前，覆核者與被覆核者要先講定量測的樹與 ref**，否則兩邊量的是兩個世界。

2026-08-23 同日實踩：一份報告裡**混了兩棵樹**——有些值用 `git show <ref>:<file>` 量、
有些用裸 `grep <file>` 打在**落後幾十顆的本機工作樹**上。
⚠ **兩種輸出長得一模一樣**，而且**正確的那幾個會讓錯的那幾個看起來也驗過了**。

⇒ 這與 [§4](#4--為什麼驗過了還是會丟) 是同一個形狀：**輸出不可區分**。
差別只在那裡不可區分的是「載體活不活得下來」，這裡不可區分的是「你量的是哪個世界」。

⇒ 作法：報數字時**連同 ref 一起報**（`git show <sha>:<file>` 這種自帶 ref 的查法優於裸 `grep`），
覆核者用**同一個 ref** 重量。

### 然後才是逐項複驗——#798 實例逐格

1. **讀回並比對行數**：`maestri note read "<名字>"` → 派工者讀回 131 行，teammate 自報 130 行。
   ⚠ **差異要能解釋**（本例＝含 header）；解釋不出來就不是通過。
2. **內容存在性檢查**：多個內容鍵各自的命中數（本例 6 個鍵，各 4／3／3／2／1／1）。
3. **陰性對照**：`ZZZ_NOT_PRESENT` → 0 ⇒ **判準有鑑別力**。
4. **檔案型產物**：**從新位置獨立跑一次**（本例 exit 0、輸出符合預期）⇒ 證明它不是死檔，
   不是只有「檔案在」。

## 8. 已經丟了怎麼辦（止血形態）`[2026-08-23]`

原件讀不到、但內容還在你的 transcript 裡時：

1. 重建成一份掛在**你自己**節點上的 note。
2. **檔頭第一句**標明「這份是重建版，不是原件；原件若被重新連上，以原件為準——
   它含有我這裡沒有的原始輸出片段」。
3. 🔴 **誠實記帳**：**遺失的是你從沒看過的原始輸出，不是結論。**
   ⛔ 不要把「結論還在」寫成「沒有損失」。

## 9. 待補（我判斷應該有，但沒有來源）

⚠ **以下每一項在兩份實例與 2026-08-23 的補充裡都找不到出處**，所以不寫進正文。
要不要納入是團隊的決定，不是我的。

1. **複驗不通過時怎麼辦。** 兩份實例都只描述通過的路徑，沒有失敗分支
   （重做？換落點？誰決定可以放行？）。
2. **「移轉到自己名下」的具體機制與等同性驗法。** [步驟 2](#步驟-2--移轉到派工者名下-2026-08-23)
   給了原則（掛在不會被清掉的東西上），但沒給步驟：誰複製、複製後怎麼證明與原件等同
   （行數？逐字？）——而「行數相同」正是 [§4](#4--為什麼驗過了還是會丟) 說不可區分的那類訊號。
3. **dismiss 之後的事後確認。** [§4](#4--為什麼驗過了還是會丟) 說 dismiss 那一刻沒被探針涵蓋；
   直覺上該在 dismiss **之後**再讀一次自己那份，但沒有來源把它寫成步驟。
4. **保全內容的最小結構。** 兩份實例都是自由格式清單，沒有欄位規範。
5. **多位 teammate 同批收尾的順序**與彼此的交叉污染。
6. **保全內容的保留期限**——什麼時候可以清、由誰決定。
7. **本協定自己的機器守線。** 目前純散文，沒有任何 gate 在驗
   （這正是 2026-08-23 事故的形態：規則存在、但沒有東西會在你違反時響）。
